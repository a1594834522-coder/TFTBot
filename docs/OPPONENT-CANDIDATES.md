# 下一轮候选对手：证据与验证

2026-10-21：加权计算已有接口，但还没有确认可代表游戏头像候选标记的原生字段。当前仍显示全场等权参考。侦察目标、正在交战的对手、下一轮候选集合必须分别处理。

## 2026-10-21 开发记录版实局核对

本次投降局从 1-1 到 3-3 的两段保留日志共记录 1,675 条原始原生包；审计没有读取错误、无效 JSON 或原生包截断。名单事件 102 条，字段只有 summoner、tag_line、index、health、xp、localplayer、rank，没有出现候选标记字段。所有已输出胜率的记录仍是 uniform，全场等权不是下一场对手分布。

7 次 `tft_opp` 均在对应回合 `combat_begin` 约 5 秒前出现，为单个身份字符串，不能据此还原准备阶段的候选集合。原生工作进程转发全部 received payload，记录器在语义解析之外记录原包；没有在当前 TS 接收层发现按事件名过滤候选包的订阅配置。这些证据只说明本局收到的数据缺少已确认的候选信号，不能推论原生提供者在任何情况下都无法提供。

已修正 HUD：没有候选证据时显示“对手待识别 —”，展开后保留明确标注的全场参考；不再把等权百分比放在下一场胜率的位置。候选采集本身仍未完成，生产调用没有接入候选先验。后续需要建立原生候选字段契约，或用游戏头像角标画面验证视觉识别；本局日志没有录制游戏画面，不能据此宣称角标识别已验证。

已检查公开 [Overwolf TFT GEP 文档](https://dev.overwolf.com/ow-native/live-game-data-gep/supported-games/teamfight-tactics/)。其中列出 `match_info.opponent`、`roster.player_status`、战斗与回合事件，但没有明确列出头像候选标记。文档没有列出不代表当前国服提供者一定没有该信号。

原版安装包 `resources/apps/amumu.bin` 中 `assets/trick-8da003d2.js` 的处理逻辑使用 `tft_roster` 刷新名单、把 `team_opp` 存入历史并在战斗结束时处理；没有据此证明 `team_opp` 就是下一轮候选名单。`tft_opp` 的存在同样不能证明候选语义。静态 DLL 字符串检索也未建立候选字段契约。

采用 REA 静态分析，工作区临时证据保留在 `dist/opponent-focused-rea.json`；原始提取文件仅保留在忽略目录中，不提交原版二进制或提取源码。

## 已准备的采集

工作区启动脚本开启本地监控。`opponent-signal-probe` 记录：

- 玩家名单中未知字段的类型、原始值及其变化；单纯血量、经验、名次变化不反复采样。
- 回合、战斗、对手相关事件，连同当时回合号。
- 现有解析器尚不认识的新事件，保留 `accepted:false`，不会因拒绝解析而丢失证据。
- 重复事件去重、节流、大小与累计量限制；保留名单与未知事件各自的配额。

探针不推断字段含义，也不修改候选名单或胜率权重。合成测试中的字段名明确是测试数据，不是宣称已经存在的 GEP 字段。

分析命令：

```powershell
node scripts/audit-opponent-signals.mjs
```

报告写入 `dist/opponent-signals/report.json`。所有实战日志留在本机，不推送 GitHub。

## 待实战确认

需要对照准备阶段头像角标与同一时刻原生事件，验证字段是否真的表示完整候选集合；继续观察回合切换、玩家淘汰和候选刷新时的变化。没有实际概率时，只能在已验证的候选内部等权，不能凭角标编造更细的匹配概率。

接入后还需保证跨回合失效、玩家身份对应、淘汰玩家处理以及未知候选战力的概率质量不被丢弃。战斗预测和购物比较必须使用同一份权重。若原生通道确实没有该字段，可另做头像角标视觉识别，并校对行位置与玩家身份；今天没有游戏画面，尚未实现或验证该视觉方案。
